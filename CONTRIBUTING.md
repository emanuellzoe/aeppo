# Contributing

Thanks for helping improve aeppo. It is a small, zero-dependency scanner, and the rules below keep it that way.

## Ground rules

- **Never run code from a repository you are testing against.** Clone it shallowly, read it as text, and scan it with aeppo. Do not install its dependencies, run its build, or open it in an IDE that executes tasks or build scripts on open.
- **No runtime dependencies.** aeppo runs on the Python standard library only, on Python 3.9 and newer.
- **Tests never use the network.** OSV.dev lookups are tested with a fake `fetch` (see `tests/test_osv.py`).
- **Corpus samples are inert.** Commands are harmless (`echo hi`), URLs use the reserved `.invalid` domain, and network addresses use documentation ranges (`192.0.2.0/24`). Secrets and bidirectional control characters are generated by `tests/test_corpus.py`, never committed.

## Development

```sh
python -m unittest discover -s tests   # all tests, including the detection corpus
python scripts/benchmark.py --max-ratio 120   # scan speed relative to reading the files
python -m aeppo scan .   # aeppo scans itself; .aeppo.toml excludes the corpus
```

## Layout

| Module | Contents |
|---|---|
| `aeppo/scanner.py` | File discovery, suppression comments, fingerprints, baselines, dispatch |
| `aeppo/findings.py` | `Finding` and the `RULES` registry (message, severity, confidence, category, recommendation) |
| `aeppo/rules_python.py` | Python AST rules |
| `aeppo/rules_js.py` | JavaScript and TypeScript rules |
| `aeppo/rules_secrets.py` | Secret patterns and Trojan Source |
| `aeppo/rules_deps.py` | `requirements.txt` and `package.json` |
| `aeppo/rules_shell.py` | Shell scripts; also used for commands embedded in other files |
| `aeppo/rules_actions.py` | GitHub Actions workflows |
| `aeppo/rules_autoexec.py` | Files that run on open, build or install |
| `aeppo/lexer.py`, `aeppo/rules_code.py` | Go, Rust, Java/Kotlin, PHP and Ruby |
| `aeppo/check.py` | `aeppo check`: hardened clone, sections and verdict |
| `aeppo/lockfiles.py`, `aeppo/osv.py`, `aeppo/rules_vulns.py` | Lockfile parsers, the OSV.dev client and `VULN001`/`MAL001` (`--osv`) |

## Adding or changing a rule

1. Add the rule to `RULES` in `aeppo/findings.py` with a recommendation a reviewer can act on.
2. Implement it in the matching `rules_*` module. Keep a cheap substring prefilter in front of regexes and parsing; the benchmark fails CI on large slowdowns.
3. Add at least one positive and one negative sample under `tests/corpus/`, with an entry and a reason in `tests/corpus/expected.json`. Limitations go in `tests/corpus/known_miss/`.
4. Scan a few real repositories (as text) and look at every new finding. Fix false positives before submitting, and mention the repositories in the pull request.
5. Document the rule in the README tables and add a line under "Unreleased" in `CHANGELOG.md`.

## Pull requests

Every change goes through a pull request. CI runs the tests on Python 3.9 to 3.13, the corpus summary, the benchmark and an Action smoke test; `main` requires them to pass. Pull requests are squash merged.

## Releases

1. Bump `__version__` in `aeppo/__init__.py` and move the "Unreleased" notes in `CHANGELOG.md` under the new version.
2. Merge, then create a GitHub release on the merge commit. Publishing the release uploads the package to PyPI.
3. Update the full-SHA pins (`# vX.Y.Z`) in the README examples.
